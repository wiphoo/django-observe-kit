# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Security
- **Breaking:** inbound W3C `traceparent` / `tracestate` headers are no longer extracted by default. Set `OBSERVE_KIT["TRUST_INCOMING_TRACE_CONTEXT"] = True` (mesh-internal services) or list trusted client IP / CIDR blocks in `OBSERVE_KIT["TRUSTED_TRACE_SOURCES"]` to restore propagation. Prevents trace-id poisoning, forced-sample DoS on the trace backend, and `tracestate` injection from untrusted edges. See [#4](https://github.com/wiphoo/Django-Observe_Kit/issues/4).
- Cap Prometheus `route` / `tenant` label cardinality at `OBSERVE_KIT["METRICS_MAX_LABEL_CARDINALITY"]` distinct values per process (default 1000; `0` disables). Stops attacker-controlled inputs — raw 404 paths, `X-Tenant-Id` headers, subdomain probes — from inflating Prometheus time-series count. See [#9](https://github.com/wiphoo/Django-Observe_Kit/issues/9).
- Sentry `before_send` scrubbing now applies the `PII_LEVELS["sentry"]` level to every event field that can carry PII — request headers (dict or list-of-pairs), `query_string` (dict, string, or list-of-pairs), top-level `tags` (duplicate params preserved) and the query component of `request.url` (and URL values embedded under `url` keys in bodies/extra/breadcrumbs), the body (`request.data` — parsed dict, positional list, list-of-`[key, value]` form pairs (key rules applied per pair), or a raw JSON/form string; unparseable bodies and valid-but-scalar JSON bodies (`"phone=…"`, a bare number) redacted wholesale rather than reparsed as a form), the `user` object (e.g. `user.email` masking), application `extra`, custom `contexts` (`sentry_sdk.set_context`), free-text message fields (`message` / `logentry` — including its interpolation `params`, whether a positional tuple or a named dict; tuples are normalised and dict args get the key-based rules before pattern-scrubbing — and breadcrumb `message`, with embedded emails/URLs masked), exception `value` text, breadcrumb `data`, transaction `spans[*].data` / `spans[*].description` (db/cache statements redacted; other descriptions get an explicit `description` operator rule (`EXTRA_MASK_FIELDS={"description"}` / drop / hash) first, else are pattern-scrubbed for embedded URLs *and* emails; db/cache redaction includes the legacy `db.statement` and current OTel `db.query.text` / `db.query.parameter.*` span-data keys, in dict and list-of-pairs form and regardless of value type — a non-string bind value like an IN-clause array `["0812345678"]` is redacted wholesale, not recursed into) and the `transaction` name, URL-valued request headers (`Referer`, etc. — query scrubbed in dict, list-of-pairs, and CGI-env forms). Unambiguous email tokens are masked even under a non-sensitive key wherever they appear — every string leaf of the event (`tags`, `extra`, `contexts`, header/env values, query values in string/dict/list form, list elements, …), not just `MASK_FIELDS` keys, and whether the address is literal or percent-encoded (`alice%40example.com`, including an encoded local part `alice%2Btag%40…`, an encoded domain dot `alice%40example%2Ecom`, or encoded TLD letters `alice%40example%2E%63%6f%6d`) in a free-text/generic leaf. An email in a query *parameter name* (`?alice@example.com=1`) is masked as well, not just the value. A URL / relative URL stored as a bare positional list element (`request.data=["/search?phone=…"]`, `extra={"redirects": [...]}`) has its query scrubbed too, like dict / pair values. A relative URL carrying a query in a free-text field (`GET /search?phone=…` in a message, exception value, or non-db span description) has its query scrubbed too — the same field rules that apply when the URL is absolute or stored in `request.url`. A query-parameter value that is itself a URL or carries a nested query (`next=/search?phone=…`, a redirect target) is recursively scrubbed so its inner parameters get the field rules instead of being re-emitted raw — in the raw-string, dict, and list-of-pairs `query_string` forms alike, and even when the redirect is double-percent-encoded (`next=%252Fsearch%253Fphone%253D…`, which `parse_qsl` decodes only one layer) — the value is percent-decoded before deciding it carries no nested query. Request fields already fully scrubbed by the request pass — a raw `request.data` string body, `query_string` (all shapes), the CGI/WSGI `env`, and the request `headers` — are kept out of the whole-event walk (only the idempotent email backstop is re-applied), so a serialized JSON body isn't re-detected as a URL and corrupted into invalid JSON, and a nested hashed param (`token=…` inside a `next=…` redirect) isn't hashed a second time — it stays the same single `sha256` as the same value in `request.url`. A raw `request.data` JSON body that decodes to a list of `[key, value]` pairs is scrubbed key-aware (like the parsed pair-list form) rather than positionally. Every scrubbed URL also has any `user:password@` credentials in its authority redacted, email tokens masked in the path (literal or percent-encoded `%40`, not just the query), and a query-like or email-bearing fragment (`#access_token=…` / `#email=…`, percent-encoded forms included) redacted wholesale (plain anchors kept) — across request URL, span `http.url` / `url.full` / `http.target` / `url.path` and the `http.path` tag (the path+query and bare-path attributes this repo's OTel middleware / `SentryContextMiddleware` emit, scrubbed in dict and list-of-pairs forms), breadcrumbs, referer headers, and embedded URLs; a malformed URL whose authority carries credentials is redacted wholesale rather than passed through. and captured stack-local `vars` in exception/thread frames. These URL / query / statement / free-text values are rewritten by a single recursive value walk over the event, so new PII-carrying fields are absorbed by extending a key set rather than adding another bespoke walker. That walk is also the *single* place the operator field rule is applied to a URL / query / free-text key — in both dict and list-of-`[key, value]` pair forms, so a `url` / `http.path` / `message` pair under `extra` / `contexts` / `request.data` / `tags` gets the same URL/query/free-text scrubbing (inner query params masked, etc.) as the dict form — so a `url` field inside `extra` / `contexts` / `request.data` (or a raw JSON body, dict or pair-list) is hashed/masked exactly once — the same single `sha256` as the same value in `request.url` — instead of the earlier body pass and the walk both applying the rule and double-hashing the digest. Free-text URL detection is case-insensitive, so a mixed-case scheme (`HTTPS://…`) in a message / span description is scrubbed too. Transaction (trace) events are scrubbed via `before_send_transaction` (previously only error events were scrubbed) — not just request headers, and honours the operator's `EXTRA_DROP_HEADERS` / `EXTRA_MASK_FIELDS` / `EXTRA_HASH_FIELDS` extensions. `request.cookies` is redacted wholesale (any shape). The CGI/WSGI `request.env` (Django `META`) is scrubbed too — `HTTP_*` header entries get the header rules (`HTTP_AUTHORIZATION` / `HTTP_COOKIE` dropped, etc.), for `QUERY_STRING` and the URI-mirror entries (`REQUEST_URI` / `RAW_URI` / `PATH_INFO`) an explicit operator rule keyed by the lower-cased env name (`EXTRA_DROP_HEADERS` / `EXTRA_MASK_FIELDS` / `EXTRA_HASH_FIELDS`, e.g. `{"path_info"}`) is applied first and only the unhandled remainder is query/URL-scrubbed — so a secret in a non-email path segment is dropped/masked/hashed by the operator rule instead of surviving the URL scrub — `*_COOKIE` env keys (Django's `CSRF_COOKIE` secret) are redacted wholesale like `request.cookies`, and non-`HTTP_` WSGI keys (`REMOTE_USER`, custom keys) honour the operator's `EXTRA_MASK_FIELDS` / `EXTRA_DROP_HEADERS` by key name. Tuple- and set-shaped event values (e.g. `set_extra("cc", ("a@b.com",))` or `set_extra("cc", {"a@b.com"})`) are normalised at every depth so their leaves are scrubbed — normalisation strips the walk-managed keys so a tuple-contained `url` is hashed once (the same single `sha256` as `request.url`), not double-hashed — and a malformed URL's surviving path has its emails masked. Free-text URL detection also covers scheme-relative `//user:secret@host/path` URLs, whose `user:pass@` credentials are redacted — including when such a URL is a nested query / redirect value (`next=//user:secret@host/…`). A standalone `request.fragment` carrying an OAuth token / query (`access_token=…`, `email=…`) is redacted like the `#…` fragment of `request.url` (a plain anchor is kept). `logentry.params` named-argument dicts get the same key-aware scrubbing as span data: a `db.statement` / `db.query.parameter.*` bind value is redacted and a `url` / `http.query` value gets the URL/query field rules, not just free-text email/URL masking. At `SENSITIVE` the client IP is hashed with `PII_HASH_SALT` wherever it appears — `request.env.REMOTE_ADDR` and forwarded `HTTP_X_FORWARDED_FOR` / etc., `user.ip_address`, and proxy-forwarded IP headers (`X-Forwarded-For`, `X-Real-IP`, etc.) — single-hashed so the values stay consistent even when `ip_address` or a forwarded-IP header (e.g. `x-forwarded-for`) is in `EXTRA_HASH_FIELDS` — the header/env mapping pass skips those so the digest is never hashed twice. An explicit `EXTRA_MASK_FIELDS` / `EXTRA_DROP_HEADERS` rule for a client-IP field (`remote_addr`, a forwarded-IP header, `ip_address`) wins over the IP hash — the field is left masked/dropped rather than being hashed back over — and such a rule is honoured whether it's keyed by the CGI/env name (`remote_addr`) or the semantic alias (`ip`). Likewise a field-level rule keyed by the container name (`query_string`, `url`, `transaction`, `data` — the whole request body) is applied before the URL/query/body scrub, so an explicit drop/mask/hash of the whole field wins over parsing its individual parameters; the same holds for free-text fields (`message` / `formatted` / `value` — top-level, breadcrumb, and logentry messages, exception values) so an `EXTRA_MASK_FIELDS={"message"}` / drop / hash rule masks or redacts the whole field instead of leaving a non-email secret (`token=…`) that the free-text scrub alone would keep, and for the `logentry.params` interpolation-args subtree (an `EXTRA_DROP_HEADERS={"params"}` / mask / hash rule redacts/masks/hashes the whole field before its leaves are pattern-scrubbed, so a positional `["supersecret"]` doesn't survive). See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).

### Fixed
- Sentry PII scrubbing: URL-valued request headers supplied as `(name, value)` **tuple** pairs (not just `[name, value]` lists) are now scrubbed. Previously `_scrub_url_headers` mutated a throwaway copy (silently leaking the `Referer` query) and `_scrub_url_values` raised `TypeError` on the tuple assignment (aborting `before_send` and dropping the event); both now write back through a shared helper. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- PII field rules: the `aliases` lookup in `sanitize_mapping` is now case-insensitive, so a differently-cased mapping key (`Remote_Addr`) still matches its `remote_addr` alias and the client IP is hashed at `SENSITIVE` instead of stored raw. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- Sentry PII scrubbing: percent-encoded `REQUEST_URI` / `RAW_URI` env mirrors (e.g. `%2Fsearch%3Fphone%3D…`) are now bounded-decoded before scrubbing, so their hidden query delimiters are exposed and inner PII (a masked `phone`, …) is scrubbed instead of shipped raw. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- Sentry PII scrubbing: the whole-event email backstop now also masks RFC 5321 *domain-literal* addresses (`alice@[192.0.2.1]`, `bob@[IPv6:2001:db8::1]`) in messages, extras, query values, and generic leaves, instead of leaving the local part recoverable. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- Sentry PII scrubbing: a benign doubly-encoded percent (`%2525`, e.g. `progress=100%2525`) is no longer redacted to `[Filtered]`. The generic-leaf email backstop now bounded-decodes and redacts only when an actual email indicator surfaces, preserving captured context. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- **Breaking-ish:** `PrometheusRequestMiddleware` no longer falls back to the raw request path when route resolution fails. Unresolved requests now collapse to `route="unknown"` instead of producing a new label series per probed URL. Dashboards that filtered on specific 404 paths will need to switch to `status="404"`. See [#9](https://github.com/wiphoo/Django-Observe_Kit/issues/9).

### Added
- `OBSERVE_KIT["METRICS_AUTH"]` setting (`"none"` | `"staff"` | `"token"`) and `OBSERVE_KIT["METRICS_TOKEN"]` to gate the Prometheus `/metrics` endpoint. Token mode uses constant-time comparison. When mode is `"none"` and Django `DEBUG` is `False`, a one-shot `RuntimeWarning` is emitted to flag the unauthenticated endpoint. See [#2](https://github.com/wiphoo/Django-Observe_Kit/issues/2).
- Startup validator that warns when `django.conf.settings.MIDDLEWARE` contains `observe_kit` middlewares in the wrong order or omits a required entry. Advisory only — never raises. Opt out via `OBSERVE_KIT["VALIDATE_MIDDLEWARE_ORDER"] = False`. See [#7](https://github.com/wiphoo/Django-Observe_Kit/issues/7).
- OTEL tracing with automatic W3C trace-context propagation plus the `X-Trace-Id` header.
- Per-sink PII configuration (`PiiConfig`) spanning logs, OTEL, Sentry, and audit sinks.
- DRF integration middleware that detects ViewSet actions and renames spans to `drf.<ViewSet>.<action>` while tagging frameworks.
- Structured logging, audit entries with trace IDs, request body sanitization, and optional DB-tracking controls.
- Health checks, validation helpers, and documentation that explain advanced usage and observability guardrails.

### Changed
- `configure_logging`, `init_tracing`, and `init_sentry` now validate inputs, honor per-sink PII, and document the new defaults.
- Body sanitization (`sanitize_body`, used by all sinks — logs, OTel, Sentry, audit) now normalizes `tuple` / `set` / `frozenset` databags to lists and sanitizes their nested dicts/leaves, instead of passing them through unscrubbed. It also recognizes a list of `[key, value]` string-keyed pairs (e.g. `set_extra("form", [["authorization", …], ["phone", …]])`) at any depth and applies the field rules by each pair's key — like a dict — instead of treating it positionally and leaving secrets under known keys raw. Genuine positional arrays / numeric matrices are unaffected. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- Audit rows now apply the `audit` sink PII field rules to the dedicated `remote_addr` / `user_agent` columns (previously only `extra` / `_before` / `_after` bodies were scrubbed). At `SENSITIVE` the client IP and user-agent are hashed with `PII_HASH_SALT` — and any operator `EXTRA_DROP_HEADERS` / `EXTRA_MASK_FIELDS` / `EXTRA_HASH_FIELDS` rule keyed by *either* the DB column name (`remote_addr` / `user_agent`) or its semantic alias (`ip` / `user-agent`) is honoured — instead of being stored raw. At `BASIC` they remain unchanged. See [#22](https://github.com/wiphoo/Django-Observe_Kit/issues/22).
- Middlewares gain graceful error handling, framework detection, and tighter span naming for DRF routes.
- Metrics, health checks, and Wagtail hooks now surface tenant/trace metadata consistently.

### Fixed
- Missing trace_id propagation in audit logs and logging handlers.
- DRF action detection gaps, Wagtail admin tagging, and middleware exceptions that previously halted requests.
- Misleading ValidationError documentation and coverage gaps around core middleware.
